# 输出长度纪律：Feishu/微信/mesh 长内容处理

## 背景

用户明确纠正：飞书消息过长会直接投递失败；助手不能把 mesh 原始返回、长审计报告、base64 分片或完整大段方案直接贴到聊天里。云端 Hermes 的稳定做法是：短消息 + 分段 + 文件附件/路径。

## 默认阈值

- 飞书/微信普通对话：单条默认 <= 800 字。
- cron/研报 final：建议 <= 500 字。
- 超过 1200 字：默认落文件，不直接贴聊天。

## 分段规则

如果用户确实要在聊天里看长内容：

1. 第一条只发“结论 + 目录 + 将分几段”。
2. 后续按 `1/3、2/3、3/3` 或类似编号分段。
3. 每段只讲一个主题：结论、证据、执行表、风险、下一步，不混在一条里。
4. 不把 Markdown 巨表、原始 JSON、日志、base64 塞进单条消息。

## 必须落文件的内容

以下内容默认写到 `.md/.txt/.html/.docx`，聊天只发摘要 + 路径/附件：

- 全量持仓表
- report_candidate_pool / 候选池
- 审计报告 / 回归报告
- 研报正文 / 字幕正文
- 代码审计
- mesh GET 原始 JSON
- base64 分片、大 tar 包内容
- 超过 1200 字的完整方案

## mesh 专用流程

用户说“看下 mesh / 完整阅读后告诉我”时：

1. 读取 mesh。
2. 把完整 JSON 保存到 `~/Desktop/hermes/mesh/mesh_inbox_latest.json` 或带时间戳文件。
3. 对每条消息只抽取：文件名、sender、字数、主题、是否为 base64/manifest/需要复核。
4. 如果要完整阅读超长正文，先保存为本地文件再处理，不把原文贴回。
5. 最终回复只给短结论、关键发现、下一步；必要时提供本地文件路径。

## 大包/base64 汇报格式

只汇报：

```text
收到大包：<package>
parts: N/N
size: <bytes>
sha256: <hash>
状态：齐全/缺part_xxx/待解包验证
```

不要贴 base64 正文。

## 失败模式提醒

- 不要因为工具返回了超长 stdout 就直接总结前几万字；先落文件再过滤。
- 不要在飞书里输出完整 `curl GET /` 结果。
- 不要把“完整阅读”误解成“完整贴给用户”。用户要的是读完后的可用结论。
