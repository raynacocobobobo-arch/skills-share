# 文档审阅器

AI 直接在 Word 文档副本里做“可视化审阅标注”：不复制粘贴，不破坏原格式，老板打开就能看到“哪里改、为什么改”。

## 重要定义：三种输出模式

### A. 审阅标注版（默认，用户最常用）
- 形态：原文保留，在段落内用**删除线/高亮/行内批注标签**标出问题，文末附“审阅摘要”。
- 适用：脚本压缩、文案改稿、合同/方案审阅、让用户快速判断哪些该删改。
- 约束：这是“可视化审阅标注”，不是 Word 原生气泡批注，也不是 Track Changes。
- 命名：`原文件名_审阅.docx` 或按任务命名为 `*_优化审阅标注版.docx`。

### B. 净稿版
- 形态：直接输出优化后的最终文本，不保留删改痕迹。
- 适用：用户说“直接改好”“给我最终版”“不要标注”。
- 命名：`*_优化版.docx` / `*_最终版.docx`。

### C. Word 原生修订模式版（谨慎使用）
- 形态：写入 OOXML `w:ins/w:del` Track Changes，可在 Word 审阅里接受/拒绝。
- 适用：用户明确说“必须是 Word 审阅模式/Track Changes/可接受拒绝修订”。
- 硬约束：不能用红字删除线+蓝字下划线假装 Word 审阅模式；如果无法可靠生成，必须直说并改用 A 模式。
- 实操注意：逐句/短语级 diff 优于整段删除+整段插入；整段替换在 Word 里观感很差。

## 核心能力

- **行内批注标签**：在段落末加“🟢/🟡/🔴 批注：……”说明原因
- **删除线（Strikethrough）**：标记建议删除的内容
- **高亮（Highlight）**：标注需要关注的部分
- **审阅摘要**：文末汇总问题和严重程度
- **默认生成副本**：不覆盖原文件，保留原文档

## 工作流程

### Step 1：用户提供文档和审阅要求

三种触发方式：

1. **只给文档**：`审阅这个合同 ~/Desktop/合同.docx`
   → Agent 按通用标准审查（逻辑漏洞、表述歧义、格式问题）
   
2. **给文档 + 具体要求**：`审阅这个方案，重点看预算部分 ~/Desktop/方案.docx`
   → Agent 按指定方向重点审查

3. **给文档 + 参考标准**：`按广告法审查这个宣传片脚本 ~/Desktop/脚本.docx`
   → Agent 按法规/标准逐条核对

### Step 2：提取文档全文

```bash
python3 ~/.hermes/skills/business/doc-reviewer/scripts/doc_reviewer.py <文档路径> --extract
```

返回带段落编号的全文，供 AI 分析。

### Step 3：AI 逐段分析

根据审阅要求，对文档逐段分析，输出结构化审阅意见：

```json
[
  {
    "paragraph": 3,
    "type": "comment",
    "original_text": "",
    "text": "这段表述有歧义，"乙方"指代不清，建议明确为"北京恩万文化传媒有限公司""
  },
  {
    "paragraph": 5,
    "type": "delete",
    "original_text": "甲方有权随时终止本合同",
    "text": "该条款对乙方保护不足，建议删除或增加双方协商终止条件"
  },
  {
    "paragraph": 8,
    "type": "modify",
    "original_text": "30个工作日",
    "text": "付款周期过长",
    "suggestion": "15个工作日"
  },
  {
    "paragraph": 12,
    "type": "highlight",
    "original_text": "违约金为合同总额的300%",
    "text": "违约金比例异常，请核实是否有法律依据"
  }
]
```

字段说明：
- `paragraph`：段落序号（从 1 开始）
- `type`：comment（批注）/ delete（删除）/ modify（修改）/ highlight（高亮）
- `original_text`：原文中要标记的具体文字（用于准确定位）
- `text`：批注/修改理由
- `suggestion`：建议替换的文本（仅 modify 类型）

### Step 4：写入审阅标记

```bash
python3 ~/.hermes/skills/business/doc-reviewer/scripts/doc_reviewer.py <文档路径> reviews.json
```

在原文档同一目录生成 `原文件名_审阅.docx`，保留原始格式，只添加审阅标记。

### Step 5：输出审核摘要

```markdown
# 审阅摘要

**文件**：合同.docx → 合同_审阅.docx
**审阅类型**：合同审查
**共发现**：X 处问题

## 按严重程度
- 🔴 严重：N 处（法律风险、重大歧义）
- 🟡 注意：N 处（表述不清晰、建议优化）
- 🟢 建议：N 处（措辞改进）

## 主要问题
1. ...
2. ...
```

## 支持的审阅类型

| 审阅类型 | 检查重点 |
|---------|---------|
| 合同审查 | 权利义务对等性、违约责任、付款条款、终止条件、歧义表述 |
| 方案评审 | 逻辑结构、预算合理性、时间线可行性、交付物明确性 |
| 脚本改稿 | 表述流畅度、信息准确性、合规性、受众适配度 |
| 简历优化 | 措辞专业度、亮点突出度、冗余内容 |
| 报告批注 | 数据一致性、结论支撑度、结构完整性 |
| 通用审阅 | 错别字、格式问题、表述歧义、逻辑漏洞 |

## 原则

1. **先确认用户要哪种审阅形态**：
   - 要“批注/意见/为什么改” → 用 `doc_reviewer.py`，可加批注、删除线、高亮、文末摘要。
   - 要“类似 Word 审阅模式直接改出来，不要批注” → 必须用真实 Track Changes，调用 `scripts/track_changes_no_comments.py`，只写入 `<w:ins>/<w:del>`，不加批注、不加摘要。
2. **不破坏原格式**：标题样式、段落间距、表格全部保留。
3. **先给副本**：默认生成 `_审阅.docx` / `_修订无批注.docx` 副本，不覆盖原文件。
4. **精准定位**：用段落编号和原文精确匹配，不凭感觉指位置。
5. **说明理由仅在用户要批注时出现**：用户明确不要批注时，不能追加“批注”“审阅摘要”“修改理由”。
6. **不要用红字删除线/蓝字下划线模拟 Word 审阅模式**：这不是用户要的 Word Track Changes。必须写 OOXML 的 `<w:ins>` / `<w:del>`，并开启 `settings.xml` 中的 `<w:trackRevisions/>`。
7. **避免整段删除+整段插入**：正常改稿应尽量做逐句/短语级 diff，只让改动处显示修订；整段替换会让 Word 里非常难读。
8. **验证后再交付**：交付前检查 docx 内 `word/document.xml` 包含 `<w:ins>` 和 `<w:del>`，`word/settings.xml` 包含 `<w:trackRevisions/>`；如果用户不要批注，还要确认没有 `word/comments.xml`。
9. **默认激活**：用户说“改脚本”“改文案”“修改这个合同”等任何涉及修改现有 Word 文档的任务，默认使用本技能。不要重新生成文档，而是在原文件上打修订标记。

## 无批注真实 Word 修订模式

当用户说“不要批注”“直接像审阅模式改出来”“Word审阅模式不是这样的”时，使用支持脚本：

```bash
python3 ~/.hermes/skills/business/doc-reviewer/scripts/track_changes_no_comments.py 原文档.docx revisions.json -o 输出_修订无批注.docx
```

`revisions.json` 示例：

```json
[
  {"paragraph": 5, "new_text": "替换后的段落文本"},
  {"paragraph": 26, "delete": true}
]
```

脚本会做中文短语级 diff，保留未改文本，只对删改部分写入真实 `<w:ins>/<w:del>`。交付时不要说“模拟审阅模式”。
