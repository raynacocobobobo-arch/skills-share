# 文档审阅器

AI 直接在 Word 原文件**副本**上做审阅或修改，保留原文档结构和格式。核心原则：**既有 Word 是基线，不是素材仓。**

## 重要定义：三种输出模式

### A. 审阅标注版（默认）
- 原文保留，用删除线/高亮/行内批注标签标出问题，文末附审阅摘要。
- 适用：脚本压缩、文案改稿、合同/方案审阅、需要用户判断删改理由。
- 这是可视化审阅标注，不是假装 Word 原生 Track Changes。
- 命名：`原文件名_审阅.docx` / `*_优化审阅标注版.docx`。

### B. 净稿版
- 直接输出优化后的最终文本，不保留删改痕迹。
- 适用：用户说“直接改好”“给我最终版”“不要标注”。
- **净稿版仍必须以原 Word 副本为基础替换/修改内容，默认保留标题、段落、表格、图片位置、样式和页面结构。**
- 禁止从空白文档重新生成一份“内容相似”的 Word 冒充“在原文件上改”。
- 只有用户明确要求“重新排版 / 新建一版 / 重做文档”时才允许重建。
- 命名：`*_优化版.docx` / `*_最终版.docx`。

### C. Word 原生修订模式版（谨慎使用）
- 写入 OOXML `w:ins/w:del` Track Changes，可在 Word 审阅里接受/拒绝。
- 用户明确要求 Word 审阅模式/Track Changes/可接受拒绝修订时使用。
- 不能用红字删除线+蓝字下划线假装 Track Changes。
- 逐句/短语级 diff 优于整段删除+整段插入。

## 跨技能衔接：领域 Skill 管“改什么”，本 Skill 管“怎么落回原文件”

当既有 Word 属于某个专业领域（宣传片、合同、营销方案等）：

1. 先加载负责**内容判断**的领域技能；
2. 再用 `doc-reviewer` 作为**文档保真与落盘层**；
3. 两者不是二选一。

### 宣传片示例

用户：“按宣传片方法论，在这个 Word 版本上改，不要重写结构。”

- Primary: `宣传片创作` —— 判断结构、受众、旁白、数据和语言怎么改。
- Supporting: `doc-reviewer` —— 以现有 Word 为基线，在副本中做最小必要修改。

**任务在长对话中从“分析/创作”变成“在现有 Word 上改”时，也要重新检查并加载本技能。**

## 原稿基线协议（修改现有文档时强制）

写入文件前先建立四栏：

- **必须保留**：用户已确认结构、标题、段落、事实、句子、格式。
- **必须修改**：用户新要求、会议修改意见、明确问题。
- **可优化**：措辞、节奏、过渡、冗余。
- **禁止擅改**：用户没有授权变化的结构/定位/关键信息。

修改目标：**最小必要改动**。不要把“我能写得更好”误当成“用户要求我重写”。

- 净稿替换；

## 工作流程

### Step 1：识别用户要的输出形态

- “给意见/为什么改/批注” → A 审阅标注版。
- “直接改好/最终版/净稿” → B 净稿版。
- “Word 审阅模式/Track Changes/可接受拒绝” → C 原生修订。

如果用户已说清楚，不要重复询问。

### Step 2：提取原文并建立基线

```bash
python3 ~/.hermes/skills/business/doc-reviewer/scripts/doc_reviewer.py <文档路径> --extract
```

返回带段落编号全文。结合领域技能生成“必须保留/必须修改/可优化/禁止擅改”。

### Step 3：逐段分析

结构化审阅示例：

```json
[
  {
    "paragraph": 5,
    "type": "modify",
    "original_text": "30个工作日",
    "text": "按当前要求需缩短付款周期",
    "suggestion": "15个工作日"
  }
]
```

字段：
- `paragraph`：段落序号；
- `type`：comment / delete / modify / highlight；
- `original_text`：精确定位原文；
- `text`：理由；
- `suggestion`：替换文本。

### Step 4：写入副本

A 模式：
```bash
python3 ~/.hermes/skills/business/doc-reviewer/scripts/doc_reviewer.py <文档路径> reviews.json
```

C 模式：
```bash
python3 ~/.hermes/skills/business/doc-reviewer/scripts/track_changes_no_comments.py 原文档.docx revisions.json -o 输出_修订无批注.docx
```

B 模式：使用原文档副本，按段落/表格/样式定位替换，不从空白 `Document()` 重建，除非用户明确要求重新排版。

### Step 5：验证

- 原文件未被覆盖；
- 标题/段落/表格/图片/样式没有因无关重建丢失；
- 修改范围符合基线；
- C 模式检查 `w:ins/w:del` 和 `w:trackRevisions`；
- 用户不要批注时确认没有多余 comments。

## 支持的审阅类型

| 审阅类型 | 检查重点 |
|---------|---------|
| 合同审查 | 权利义务、违约责任、付款、终止、歧义 |
| 方案评审 | 逻辑、预算、时间线、交付物 |
| 脚本改稿 | 表述、准确性、受众、结构、时长 |
| 简历优化 | 专业度、亮点、冗余 |
| 报告批注 | 数据一致性、结论支撑、结构 |
| 通用审阅 | 错别字、格式、歧义、逻辑 |

## 原则

1. **既有 Word 是基线**：默认复制原文件后修改，不重建。
2. **领域判断优先交给领域技能**：doc-reviewer 不替代宣传片/合同/营销等专业方法论。
3. **不破坏原格式**：标题、段落、表格、图片和样式尽量原位保留。
4. **先给副本**：不覆盖原文件。
5. **精准定位**：段落编号 + 原文精确匹配。
6. **说明理由按用户需求**：不要批注就不加审阅摘要。
7. **真实 Track Changes 就用真实 OOXML**：不模拟。
8. **避免整段删除+整段插入**：优先短语/句子级 diff。
9. **验证后交付**：不能只看生成成功。
10. **用户说“在这个版本上改”时默认激活**：尤其是在长对话后半段新增 Word 原稿时，必须重新路由。
